# Аутентификация — рекомендуемый подход

## Выбор: invite-ссылка + email с учётными данными

Для корпоративного self-hosted сценария рекомендуется **комбинация двух простых каналов**:

### 1. Invite-ссылка (основной способ онбординга)

Администратор создаёт пользователя → сервер генерирует **одноразовую ссылку**:

```
egogo://auth/invite?token=<signed_token>&server=https://api.company.com
```

| Параметр      | Значение                    |
|---------------|-----------------------------|
| TTL           | 72 часа                     |
| Использований | 1                           |
| Подпись       | HMAC-SHA256 с server secret |

При переходе по ссылке клиент:
1. Открывается автоматически (custom URL scheme `egogo://`)
2. Пользователь задаёт пароль (или подтверждает временный)
3. Профиль организации добавляется в клиент

**Почему не только логин/пароль по почте:** пароль в plaintext в email — риск. Invite-ссылка безопаснее: токен одноразовый, пароль пользователь задаёт сам.

### 2. Email с учётными данными (fallback)

Если custom URL scheme недоступен (корпоративная политика):

- Администратор создаёт аккаунт
- Сервер отправляет email с **временным паролем** (действует 24 ч, принудительная смена при первом входе)
- В письме — URL сервера и логин

### 3. Обычный логин

После первого входа — стандартный логин/пароль в клиенте.

## Поток для организации

```
Admin → создаёт пользователя на сервере
      → отправляет invite-ссылку (Slack / email / Teams)
User  → кликает ссылку → egogo client открывается
      → задаёт пароль → профиль «Acme Corp» появляется в списке
```

## Локальный профиль «My»

Не требует аутентификации. Создаётся при первом запуске клиента.
